## Folder suitability is advisory

The selected source folder may be an application root, a folder of components, or a folder containing a single component. Review visual components reached from application source as well as standalone library components. Do not narrow discovery based on folder names, component names or framework labels; determine eligibility from source semantics and applicable execution conditions.

- Trace application chrome to the output it contributes and any application providers, runtime or environment it actually depends on. Quote the relevant imports, declarations, uses and conditions; distinguish a demonstrated dependency from an unresolved possibility. A visual component depending on application setup can still be useful on a page. Record what must be checked without claiming it is ready to render independently.
- Missing imports or declarations are evidence gaps, not proof that a component is nonvisual or has nothing to author. Record the unresolved import or declaration and the affected claim in `modelingNotes` and the report. Recommend project/compiler/dependency setup when the source justifies that check, or a relevant source folder when the needed declarations are elsewhere. Do not install dependencies, invent missing contracts, remove source fields or claim exhaustive coverage.
- Describe directly authored content separately from useful design, placement or composition. When the available source establishes little or no directly authored content, cite the actual inputs and output flow and explain what an editor could still place, style or compose, including visual components driven entirely by live data. If the source is incomplete, say that the amount of authored content is unknown. Do not automatically exclude components for low static content or apply a suitability score or threshold.
- Put concrete dependencies, evidence gaps and low static-content observations in the existing `modelingNotes` and human report, with source locations, conditions, uncertainty and an actionable choice: keep useful visual components, review required application setup, or choose a relevant source folder for the intended page content. These notes are advice; they do not replace `included` or `inclusionReasoning`, and only demonstrated source reasons justify exclusion.

## Complete union decisions

When a desired content representation contains `DiscriminatedUnion`, report the complete recursive CDF property in `definition`, with `type` and `category` matching it. Preserve at least two complete `record` members, `discriminator`, every member field and its requiredness, and a required intrinsic `Literal` tag with `value` and `valueType`. Keep string, number and boolean tags typed; a default is separate from the intrinsic tag. Retain all exact compiler members and declared finite field domains; observed callers do not establish membership. Union definitions are one atomic decision, including when nested inside another representation. Do not also emit `values`, token metadata or `representationProposal` for that decision; duplicated description, requiredness and default metadata must agree with the complete definition. An unresolved source association stays unresolved, with its facts and modeling notes retained. Local desired validity does not establish mapper, cardinality or reconstruction readiness.
